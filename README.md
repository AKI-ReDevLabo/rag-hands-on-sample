# rag-hands-on

書籍のサンプルリポジトリ。Qdrant ＋ FastAPI ＋ Claude API で作る、最小構成の社内文書RAG。
`data/` の社内文書は書籍サンプル用のダミーで、実在の企業・団体・人物とは関係ありません。

## セットアップ

必要なもの：Python 3.10 以上、Docker（Qdrant を動かすため）。
コマンドは bash（Linux / macOS / Windows の WSL2）を前提にしています。

```bash
# 1. 依存パッケージ
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 2. 設定ファイル
cp .env.example .env
# 回答生成まで試す場合は .env の ANTHROPIC_API_KEY を設定する

# 3. Qdrant を起動
docker compose up -d

# 4. 文書を登録
python ingest.py --recreate

# 5. 検索する
python search.py "切り花 出荷"
python search.py "経費精算の提出期限は" --answer   # 回答まで生成（APIキーが必要）
```

- 埋め込みは既定で `intfloat/multilingual-e5-small`（ローカル実行・APIキー不要）。
  初回の実行時にモデルをダウンロードします
- モデルを落とさずに流れだけ確かめたい場合は `.env` で `EMBEDDING_BACKEND=dummy` にします
  （検索の品質は出ません）。埋め込みを切り替えたら `python ingest.py --recreate` で登録し直します
- `data/` の文書は `python gen.py` で作り直せます（事件簿①のノイズ文書 `data_noise/` は `python gen_noise.py`）

### リランク（Haiku）

APIキーを設定すると、hybrid 検索で広めに取った候補（既定40件）を Claude Haiku に
採点させ、関連度の高い順に並べ替えてから回答生成に渡します（既定8件）。
最高スコアが 3 未満なら「関連する文書は見つからない」（nohit）として扱います。

```bash
python search.py "経費精算の提出期限は"              # リランクあり（APIキーが必要）
python search.py "経費精算の提出期限は" --no-rerank  # リランクなし（RRF の閾値だけで絞る）
```

APIキーが無いとき、`RERANK=0` のとき、Haiku の呼び出しや採点結果の読み取りに失敗したときは、
RRF の閾値（0.20）だけで絞ります。この場合、dense 検索が必ず何かを返すため、
関係のない質問でも「見つからない」にはなりません。失敗したときは画面とログに理由が出ます。

APIキーが無くても、`RERANK_BACKEND=keyword` で簡易版のリランクを試せます。
質問の語（助詞などを除く）が候補の本文にいくつ含まれるかで 0〜10 を付けるだけですが、
並べ替えと nohit の判定の流れは Haiku 版と同じです。

```bash
RERANK_BACKEND=keyword python search.py "切り花の出荷単位"       # 語の一致でリランク
RERANK_BACKEND=keyword python search.py "社員食堂のメニューは？" # 最高スコア 0 → nohit
```

### チャットUI

```bash
uvicorn web.main:app --reload --port 8080
# → http://localhost:8080/
```

APIキーが未設定でも、検索結果までは表示されます。
画面上部に、いま有効な地雷スイッチが表示されます。

2問目以降は追加質問（continuation）として扱い、直前のやりとり（既定で3往復）を
LLM に渡します。話題を変えるときは「新しい話題」ボタンで履歴を切ります。

追加質問は「それの締切は？」のように言葉が省略されがちです。APIキーがあるときは、
直前のやりとりを元に Haiku が検索用の一文（例：「切り花の数量変更の締切はいつまでか」）に
書き直してから検索・リランクします。書き直した文は回答の下に「検索に使った文」として表示され、
質問ログにも `search_query` として残ります。`EXPAND_QUERY=0` で止められます。

やりとりは話題ごとにブラウザ（localStorage）に保存され、左の「過去の話題」から
開き直せます。開いた話題にはそのまま追加質問できます。保存件数の上限は
`web/static/index.html` の `MAX_THREADS`（既定50件）で変えられ、超えた分は古い順に消えます。
別のブラウザや別のPCとは共有されません。

### 登録台帳と差分登録

`ingest.py` は、どのファイルをどの内容・どの分割設定で何チャンク登録したかを
台帳（`state/ledger.sqlite3`）に記録し、2回目以降は変わったファイルだけを登録し直します
（差分登録）。分割の設定（`CHUNK_SIZE` など）を変えると、全ファイルが対象になります。
`python ingest.py --force` で全ファイルを、`--recreate` でコレクションと台帳ごと作り直せます。

台帳と Qdrant の実体がずれていないかは、`python tools/check_orphans.py` で確かめられます。

### 構造化データ層（第5章 事件簿⑤）

「会議メモは全部で何件」「拠点はいくつ」のような、数える・並べる質問は RAG では答えられません
（上位のチャンクを渡すだけで、文書の外にある事実や件数は持っていない）。
こうした質問は `structured/` が先に拾い、表を SQL で引いて答えます。APIキーは不要です。

```bash
python search.py "会議メモは全部で何件"       # RAG の検索結果の下に、構造化データでの回答が出る
python search.py "N県拠点には何名いますか"   # 書いていない数字は「データがない」と答える
STRUCTURED=0 python search.py "会議メモは全部で何件"   # RAG だけで答える（事件簿⑤の状態）
```

- 意図の判定：`structured/registry.json` のキーワード（本番は Haiku が判定）
- 表：登録台帳（どのカテゴリに何の文書があるか）と、拠点マスタ `structured/sites.csv`
- 「4月のクレームは何件」のように文書の中に書かれた数字は、これまでどおり RAG で答えます

### コード指定モード（管理番号で探す）

「KR-3104-01」のような管理番号は、dense では意味が無く、sparse では「2609」「-」「01」に砕けるので、
どちらの検索でも狙った文書に当たりません。そこで登録時に本文から管理番号を正規表現で取り出して
payload の `codes` に入れ、質問に管理番号があれば `codes` で絞り込んでから検索します。

```bash
python search.py "管理番号 KR-3105-01 の内容は？"              # コード指定モード：その企画の文書だけが出る
CODE_SEARCH=0 python search.py "管理番号 KR-3105-01 の内容は？" # 絞り込みなし：似た販促企画が並ぶ
python search.py "管理番号 KR-3105-01 の内容は？" --mode sparse  # sparse だけでは企画どうしの差がつかない
python search.py "管理番号 KR-3106-05 の内容は？"              # 存在しない番号は 0 件（似た企画で埋めない）
python tools/list_codes.py                                   # 文書ごとに取り出した管理番号を見る
```

本番では質問側の取り出しを Haiku（expand_query）が担っていました。サンプルは正規表現だけです。

### 適用期間（改定された規格の旧版を出さない）

規格や規程は改定されます。旧版がフォルダに残っていると、検索は新旧の両方を拾い、
LLM はどちらの数字を答えるか決められません。そこで登録時に、本文の
「適用期間：2025-04-01〜2026-03-31」「適用開始：2026-04-01」の行を読んで payload に入れ、
検索時は基準日（既定は今日）に有効な文書だけに絞ります。行が無い文書は常に対象です。

```bash
python search.py "リンドウは何本で1束ですか"                     # 2025年度版（10本1束）は出ない
BUG_IGNORE_VALIDITY=1 python search.py "リンドウは何本で1束ですか" # 旧版と新版が並ぶ（期間外! の印つき）
AS_OF=2026-03-01 python search.py "リンドウは何本で1束ですか"     # 改定前の日付なら旧版だけが出る
```

`BUG_IGNORE_VALIDITY=1` は、適用期間を読み込んではいるが検索では使っていない状態です。

### チャンク分割を見る（第3章）

`chunks.py` はファイルを切った結果を表示するだけで、登録はしません。

```bash
python chunks.py data/取引先対応/季節のお便り_2026秋.md          # 既定（600文字・重なり100）
python chunks.py data/取引先対応/季節のお便り_2026秋.md --raw    # 正規化なし（CR+LF で空行が見えず、段落に分かれない）
BUG_MERGE_NO_LIMIT=1 python chunks.py data/商品知識/出荷規格_切り花.md  # 併合の上限なし（600文字を超える）
```

切り方は本番と同じです。空行で段落に分け、600文字を超える段落だけを固定長（重なり100）で切り、
300文字未満のチャンクは、併合しても600文字を超えない範囲で次（末尾なら前）のチャンクに併合します。

### 地雷スイッチ（第5章の事件簿を再現する）

環境変数で「壊れた実装」に切り替えられます。既定はすべてオフです。

| 環境変数 | 事件簿 | 効果 |
|---|---|---|
| `BUG_SPARSE_UNSTABLE_HASH=1` | ① sparse がノイズ | sparse ベクトルの番号付けに `abs(hash())` を使う |
| `BUG_MERGE_NO_LIMIT=1` | ② の引き金 | 短いチャンクの併合で上限（CHUNK_SIZE）を見ない（上限チェックを足す前の分割） |
| `BUG_ORPHAN_CHUNKS=1` | ② 消したはずのチャンクが残る | 差分登録で「足りない chunk_index を足すだけ」にする（古い index も古い内容も消さない） |
| `BUG_FREE_MODE_ROUTING=1` | ③「情報がありません」 | 相槌（検索不要と判定）の追加質問を、フリーモード用プロンプトに回す（人格が入れ替わる） |
| `BUG_CONTRADICTING_RULE=1` | ③「情報がありません」 | 共通ルールに「前の回答には言及しない」を足す（追加質問の指示と矛盾する） |
| `BUG_CODE_REGEX_MATCHES_DATE=1` | コード指定モード | 管理番号の正規表現が、日付「2026-09-14」の先頭「2026-09」まで拾う |
| `BUG_IGNORE_VALIDITY=1` | 地雷⑥ 旧版の数字 | 適用期間を payload に入れるが、検索の絞り込みに使わない |
| `ANSWER_MAX_TOKENS=200` | ④ 回答が途中で切れる | 回答の最大トークン数を小さくする（既定 4096） |

```bash
# 事件簿①：登録と検索が別プロセスなので、sparse 検索が当たらなくなる
BUG_SPARSE_UNSTABLE_HASH=1 python ingest.py --recreate
BUG_SPARSE_UNSTABLE_HASH=1 python search.py "切り花 出荷" --mode sparse  # 1件も当たらない
BUG_SPARSE_UNSTABLE_HASH=1 python search.py "切り花 出荷" --no-rerank    # 単一分数に揃い、警告が出る
BUG_SPARSE_UNSTABLE_HASH=1 python search.py "切り花 出荷"     # リランクありでは、Haiku がさらに覆い隠す
BUG_SPARSE_UNSTABLE_HASH=1 RERANK_BACKEND=keyword python search.py "切り花 出荷"  # APIキーなしでも、警告が消えて結果がもっともらしく並ぶ
python ingest.py --recreate                                   # 元に戻す

# 事件簿①（ノイズ版）：文書を増やすと「0件」ではなく「もっともらしいノイズ」が返る
python gen_noise.py                                           # data_noise/ を作り直す（同梱済み）
export COLLECTION_NAME=minefield_noise EXTRA_DATA_DIR=data_noise SPARSE_DIM=4500
BUG_SPARSE_UNSTABLE_HASH=1 python ingest.py --recreate        # data/ ＋ data_noise/ を別コレクションに登録
BUG_SPARSE_UNSTABLE_HASH=1 python search.py "切り花のクレーム件数" --mode sparse   # 無関係な日誌や記録が並ぶ
BUG_SPARSE_UNSTABLE_HASH=1 python search.py "切り花のクレーム件数"   # 単一分数の警告が出る
python ingest.py --recreate                                   # 正しい実装で登録し直す
python search.py "切り花のクレーム件数" --mode sparse         # 会議メモや規格書が上位に戻る
unset COLLECTION_NAME EXTRA_DATA_DIR SPARSE_DIM               # 通常のコレクションに戻る

# 事件簿②：チャンク分割を直した翌日、差分登録が古いチャンクを残す
BUG_MERGE_NO_LIMIT=1 python ingest.py --recreate  # 直す前の分割（併合の上限なし）で登録
BUG_ORPHAN_CHUNKS=1 python ingest.py      # 分割を直して差分登録（旧実装）。台帳と実体がずれる
python tools/check_orphans.py             # 孤児チャンクと、古い内容のままのチャンクを数える
python ingest.py                          # 台帳は「変更なし」と言う。差分登録では直らない
python ingest.py --force                  # 全ファイルを登録し直して直す

# 事件簿④（APIキーが必要）
ANSWER_MAX_TOKENS=200 python search.py "ハーブは返品できますか" --answer

# 管理番号の正規表現が日付を拾う
BUG_CODE_REGEX_MATCHES_DATE=1 python ingest.py --force
python tools/list_codes.py                # 2026-09 / 2026-10 / 2026-11 が管理番号として並ぶ
python ingest.py --force                  # 元に戻す
```

#### 事件簿①のノイズ文書（data_noise/）

`data/` の25チャンクだけでは、壊れた sparse はほぼ「0件」になります。
実際の現場で見えるのは0件ではなく「それらしいが無関係な結果」なので、
量の多い文書を `data_noise/` に別に用意しています（`gen_noise.py` で生成、約59万字・約1480チャンク）。

| フォルダ | 中身 |
|---|---|
| `栽培記録/` | 圃場ごと・作ごとの記録（天気、作業、生育の計測、病害虫、積算温度やかん水量） |
| `作業日誌/` | 拠点ごと・月ごとの日誌（作業、施設点検、検針、気象、来訪、引き継ぎ） |
| `会報誌/` | 取引先店舗に配る会報誌「みどりだより」のアーカイブ（産地だより、花の豆知識、レシピなど） |

- `data/` には混ぜず、`EXTRA_DATA_DIR` と別名の `COLLECTION_NAME` を指定したときだけ登録します。
  通常のコレクションの検索結果は変わりません
- 地雷①〜⑥の答えになる事実（締切・休止・返品・品質不良・件数・人数・拠点の数・予冷の温度など）は書いていません。
  `gen_noise.py` の `check_forbidden()` が生成のたびに検査します
- 壊れた sparse が何かを返すかどうかは、チャンク数よりも**文書全体の異なる単語の数（語彙）**で決まります。
  質問の単語1つが偶然どこかの単語に当たる確率は、おおよそ「語彙 ÷ `SPARSE_DIM`」です。
  `data_noise/` を足しても語彙は約9,500語で、本番の文書より2桁ほど少なくなります。
  既定の `SPARSE_DIM=50000` のままだと、質問の約5割は0件のままで、当たっても多くは1〜数件です
- そこでノイズ版の手順では `SPARSE_DIM=4500`（語彙の約半分）にして、
  「本番の語彙と `SPARSE_DIM` の比率」を小さなデータで真似ています。
  手元の計測（下の動作確認用クエリ13問と「切り花 出荷」の14問を、各10回）では、
  140回のうち130回で5〜15件のノイズが返り、残りの10回は1〜4件でした。
  壊れた hash はプロセスごとに変わるので、件数は実行のたびに変わります
- `SPARSE_DIM` は登録時と検索時で同じ値にする必要があります。上の手順のように `export` しておきます

## 埋め込んである「地雷」

このデータは、RAGの典型的な失敗を再現するために意図的に設計しています。

### 地雷① 品目を特定しないと答えが割れる

締切も休止上限も、品目ごとに違う値を持たせています。

| 品目 | 数量変更の締切 | 一時休止の上限 |
|---|---|---|
| 切り花 | 7日前 | 1か月 |
| 乾燥ハーブ | 14日前 | 3か月 |
| ハーブ | 3日前 | 1か月 |

```
Q: 数量の変更はいつまでにすればいいですか？
Q: 出荷の一時休止は最大何か月ですか？
```

品目を指定していないので、正解は一つに定まりません。
チャンクが分割されると表の一部しか拾えず、片方の数字だけを断定して答える
という誤答が発生します。**理想的な挙動は「どの品目についてか」を聞き返すこと。**

### 地雷② 返品可否が3ファイルに分散し、しかも結論が逆

- `出荷規格_ハーブ.md` → 返品不可
- `出荷規格_乾燥ハーブ.md` → 条件付きで返品可
- `品質クレーム対応手順.md` → 品目別の一覧あり

```
Q: ハーブは返品できますか？
```

「ハーブ」という語が生ハーブと乾燥ハーブの両方にヒットするため、
検索結果に矛盾する記述が同時に載ります。どちらを採用するかで答えが変わります。

### 地雷③ 「不良ではない」という否定的事実

`出荷規格_切り花.md` と `出荷規格_乾燥ハーブ.md` に、
見た目の違和感が仕様どおりであるという記述を入れています。

```
Q: スターチスの色が薄いのは不良品ですか？
Q: 乾燥ハーブの色がロットで違うのは問題ですか？
```

根拠には「品質不良ではない」と明記されています。
ここで「不良の可能性があります」と答えたら、根拠を正しく読めていません。

### 地雷④ 一覧・件数クエリに答えられない

会議メモに件数を入れてありますが、これは文書内の記述であって、
文書の件数ではありません。

```
Q: 4月のクレームは何件でしたか？          → 答えられる（会議メモに記載あり）
Q: 会議メモは全部で何件ありますか？        → 答えられない
Q: 拠点は全部でいくつありますか？          → 答えられそうで答えられない
```

3拠点はどこにも一覧で書いていません。経費精算規程に「I県・N県・S県」と
並んで出てくるだけで、「拠点は3つ」とは書いていない。
**RAGは書いてあることしか答えられない、を示す実演素材です。**

### 地雷⑤ 書いてある人数と、書いていない人数

`拠点間異動規程.md` には「S県の常駐は4名」「寮の定員は24名」「認定者は11名」と
書いてありますが、季節雇用者の人数やN県拠点の在籍人数、拠点長の人数はどこにもありません。

```
Q: S県拠点には何名常駐していますか？  → 答えられる（4名）
Q: 季節異動の対象は何名ですか？        → 一部だけ答えられる（認定者11名。拠点長を足した合計は書いていない）
Q: N県拠点には何名いますか？          → 答えられない（寮の定員24名に引きずられる）
```

寮の定員24名という数字が近くにあるため、それを人数として答えてしまう
誤答が起きやすい設計です。数字の意味を取り違える典型例。

### 地雷⑥ 時系列で数値が更新される

4月10日の会議で「切り花のクレームは月平均12件」、
5月15日の会議で「4月は7件に減少」と書いてあります。

```
Q: 切り花のクレームは何件ですか？
```

古い方のチャンクだけを拾うと、改善前の数字を現在の値として答えます。
社内文書RAGで最も実害が出やすいパターンです。

同じ構図が、改定された規格にもあります。`出荷規格_切り花_2025年度版.md`（リンドウも10本1束）が
消されずに残っていて、現行版（リンドウは8本1束）と並んで検索されます。
こちらは文書に適用期間が書いてあるので、検索時に絞り込めます（`BUG_IGNORE_VALIDITY=1` で絞り込まない）。
会議メモの数字のように、期間の書いていない文書には効きません。
